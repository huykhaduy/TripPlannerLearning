# Coolify deployment: backend, Postgres and Redis as one Docker Compose resource

**Date:** 2026-08-14
**Status:** approved (design), not yet implemented

Deploy `TripPlanner.WebApi` to Coolify as a single **Docker Compose** resource containing
three services — `api` (built from the existing `backend/Dockerfile`), `postgres` and
`redis`. Backend only; the frontend is deployed separately and reaches the API through a
`FRONTEND_URL` env var.

| § | Change | File |
|---|---|---|
| 1 | Deployment compose file | `docker-compose.deploy.yml` (new) |
| 2 | Liveness endpoint | `backend/src/TripPlanner.WebApi/Program.cs` (2 lines) |
| 3 | `curl` in the runtime image, + fix a comment it makes stale | `backend/Dockerfile` |
| 4 | Click-path runbook | `docs/deployment-coolify.md` (new) |

Nothing else is touched. In particular the local-dev `docker-compose.yml`, `dev.ps1`,
`dev-docker.ps1`, `.env.example`, the frontend, and every file under `Application` /
`Domain` / `Infrastructure` are left alone. See §5.

---

## 1. The deployment compose file

### Why a separate file

The existing `docker-compose.yml` is a **local-dev** file: it publishes 5432 and 6379 to
the host and uses `tripplanner`/`tripplanner` as the credentials. Both are correct for a
laptop and wrong for a public host. Rather than parameterise one file into serving both
jobs — where a mistake silently exposes the database — deployment gets its own file and
the dev file stays exactly as it is.

`docker compose up -d` auto-loads only `docker-compose.yml` and
`docker-compose.override.yml`, so a third file is inert locally unless passed with `-f`.
Coolify is pointed at it explicitly (§4).

### Content

```yaml
# Coolify deployment ONLY. Local dev uses docker-compose.yml (Postgres + Redis with
# published ports and default creds); this file is never auto-loaded by
# `docker compose up`, which reads only docker-compose.yml/.override.yml.
#
# Two values are generated by Coolify rather than set by hand:
#   SERVICE_PASSWORD_POSTGRES  — a strong password, created once and remembered. Used by
#                                both POSTGRES_PASSWORD and the API connection string, so
#                                the two cannot drift. Deliberately the symbol-free
#                                variant, not SERVICE_PASSWORDWITHSYMBOLS_*: a `;` or `=`
#                                in the password would break Npgsql's connection string
#                                parsing.
#   SERVICE_FQDN_API_8080      — assigns the public domain and points the proxy at 8080,
#                                the port backend/Dockerfile listens on. Append a path
#                                (=/api) only if the API is not to sit at the domain root.
#
# No `networks:` block — Coolify creates an isolated network and warns that custom ones
# break Traefik routing. No `container_name:` — Coolify names containers per deployment.
# No `restart:` — Coolify manages restart policy. No `ports:` on postgres/redis: they are
# reachable from `api` by service name and must not be exposed to the internet.
services:
  api:
    build:
      context: ./backend
      dockerfile: Dockerfile
    environment:
      - SERVICE_FQDN_API_8080
      - ConnectionStrings__Postgres=Host=postgres;Port=5432;Database=tripplanner;Username=tripplanner;Password=${SERVICE_PASSWORD_POSTGRES}
      # Redis is switched on here (the code default is the in-process cache). Timeouts
      # match .env.example: they bound each cache call to ~1s so an unreachable Redis
      # degrades in 1-2s rather than StackExchange.Redis's ~5s+ backlog default.
      - Cache__Provider=Redis
      - ConnectionStrings__Redis=redis:6379,connectTimeout=1000,syncTimeout=1000,connectRetry=1
      # `:?` marks these required: Coolify refuses to deploy while any is blank, rather
      # than starting a container that crash-loops (Jwt__Key) or serves broken features
      # (the rest). See "Changing configuration" below for why all six are required.
      - Jwt__Key=${JWT_KEY:?}
      - Geoapify__ApiKey=${GEOAPIFY_API_KEY:?}
      - Serper__ApiKey=${SERPER_API_KEY:?}
      - Smtp__User=${SMTP_USER:?}
      - Smtp__AppPassword=${SMTP_APP_PASSWORD:?}
      # Where the browser app lives: CORS allow-list, and the base of the link in
      # verification emails.
      - Cors__AllowedOrigins__0=${FRONTEND_URL:?}
      - App__FrontendBaseUrl=${FRONTEND_URL:?}
    depends_on:
      postgres:
        condition: service_healthy
      redis:
        condition: service_healthy
    healthcheck:
      test: ["CMD", "curl", "-f", "http://localhost:8080/health"]
      interval: 10s
      timeout: 5s
      retries: 5
      start_period: 30s

  postgres:
    image: postgres:17
    environment:
      POSTGRES_USER: tripplanner
      POSTGRES_PASSWORD: ${SERVICE_PASSWORD_POSTGRES}
      POSTGRES_DB: tripplanner
    volumes:
      - tripplanner-pgdata:/var/lib/postgresql/data
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U tripplanner"]
      interval: 10s
      timeout: 5s
      retries: 5

  # No volume: this is a regenerable cache of Geoapify results. A restart costs a cold
  # cache, which is cheaper than persisting data we can always re-fetch.
  redis:
    image: redis:7
    healthcheck:
      test: ["CMD", "redis-cli", "ping"]
      interval: 10s
      timeout: 5s
      retries: 5

volumes:
  tripplanner-pgdata:
```

### Configuration set in Coolify's environment panel

Six values, all of which already exist in `.env.example` under their `__`-separated names:

| Variable | Maps to | Notes |
|---|---|---|
| `JWT_KEY` | `Jwt__Key` | Required, no default. ≥ `JwtSettings.MinKeyBytes`; `AddInfrastructure` validates it with `ValidateOnStart`, so a bad value refuses to boot rather than degrading. |
| `GEOAPIFY_API_KEY` | `Geoapify__ApiKey` | Required secret. |
| `SERPER_API_KEY` | `Serper__ApiKey` | Required secret. |
| `SMTP_USER` | `Smtp__User` | Gmail address. |
| `SMTP_APP_PASSWORD` | `Smtp__AppPassword` | Google App Password, not the account password. |
| `FRONTEND_URL` | `Cors__AllowedOrigins__0`, `App__FrontendBaseUrl` | Will be wrong until the frontend is deployed; see §6. |

Everything else — `Jwt__Issuer`, `Jwt__Audience`, `Jwt__ExpiryMinutes`, `Smtp__Host`,
`Smtp__Port`, `Geoapify__BaseUrl`, `Serper__BaseUrl` — keeps the default baked into its
settings class and is not listed in the compose file. Adding them would duplicate values
that already have one home.

`DotNetEnv.Env.Load()` in `Program.cs` finds no `.env` inside the image and returns an
empty set rather than throwing (verified against DotNetEnv 3.2.0, whose own comment reads
"in production, there should be no .env file"). Configuration therefore comes entirely
from the environment variables above, which `AddEnvironmentVariables()` reads with `__`
as the section separator.

### Changing configuration

Two different places, and they do different jobs:

- **The compose file decides *which* variables exist.** Coolify parses it and
  auto-detects every `${...}` placeholder, creating a matching field in the resource's
  Environment Variables tab. Adding a new setting therefore means editing this file and
  pushing — it cannot be done from the UI alone, because
  [the compose file is Coolify's single source of truth](https://coolify.io/docs/knowledge-base/docker/compose)
  for a compose resource.
- **The Coolify UI decides *the values*.** They are passed to `docker compose` via
  `--env-file`, so substitution happens when the stack comes up: **changing a value takes
  effect on the next redeploy, not immediately.**

Three declaration forms are available, and the choice is meaningful:

| Form | Behaviour | Used here for |
|---|---|---|
| `${VAR}` | Empty, editable field | nothing |
| `${VAR:-default}` | Field pre-filled with the default | nothing yet — the right form for a future *optional* setting |
| `${VAR:?}` | Required; deployment is blocked while blank | all six |
| `Cache__Provider=Redis` | Hard-coded, never shown in the UI | the Redis switch and both connection strings |

All six are `:?` because the API is not usefully deployed without any of them. `Jwt__Key`
is the sharpest case — `AddInfrastructure` validates it with `ValidateOnStart`, so a blank
value produces a crash-looping container, and failing at the deploy step is a far clearer
signal. The other five fail more quietly: no Geoapify key means every search returns
nothing, and missing SMTP credentials mean verification emails never arrive while
registration still reports success (`AuthService` catches mail failures by design, per
F4/US1) — leaving accounts that can never log in. `FRONTEND_URL` has a `localhost:5173`
fallback in code, which on a public host would silently produce CORS failures that are
tedious to diagnose; forcing a conscious value is worth the extra field. To deploy
without email on purpose, change those two to `${SMTP_USER:-}` rather than leaving them
blank, so the intent is recorded in the file.

Two per-variable settings in the UI matter for these:

- **Turn "Build Variable" off** on all six. Each variable carries independent Build and
  Runtime flags, both on by default; the API reads every one of these at runtime, so
  there is no reason to expose secrets to the build phase. (The frontend is the opposite
  case — `VITE_API_BASE_URL` must be a build variable, which is why `frontend/Dockerfile`
  takes it as an `ARG`.)
- **Tick "Literal"** on any value containing a `$`, typically `JWT_KEY` or
  `SMTP_APP_PASSWORD`, to stop it being interpolated.

The two magic variables appear in the same panel but are not to be edited.
`SERVICE_PASSWORD_POSTGRES` is generated on first deploy and is the only copy — read it
from there; overwriting it afterwards does **not** change the password already baked into
the initialised `tripplanner-pgdata` volume, it only breaks the API's connection string.

## 2. Liveness endpoint

Two lines in `Program.cs`, both from the ASP.NET Core shared framework — **no NuGet
package is added**:

```csharp
builder.Services.AddHealthChecks();   // with the other AddX registrations
...
app.MapHealthChecks("/health");       // next to app.MapControllers()
```

### Why no database probe

`AddDbContextCheck<ApplicationDbContext>()` was considered and rejected. It needs the
`Microsoft.Extensions.Diagnostics.HealthChecks.EntityFrameworkCore` package, and it would
answer a question the bare endpoint already answers: `ApplyMigrationsAsync` runs
**before** `app.Run()`, so the app serves no HTTP at all until migrations have finished.
A plain 200 from `/health` therefore already means "migrations applied, app accepting
requests" — which is exactly the gate Coolify needs. A DB probe would only add "the
database is still reachable *right now*", which the next real request reports anyway.

### Deliberate properties

- **Anonymous.** `MapHealthChecks` adds no `[Authorize]`, and the Docker healthcheck
  cannot present a JWT. The response body is the literal string `Healthy`; it discloses
  nothing else.
- **Outside `/api`.** Every controller route is under `/api/...`, so `/health` cannot
  collide with one.
- **Untested.** No integration test is added. The endpoint has no logic to test beyond
  the framework's own, and `TripPlanner.WebApi.Tests` exists to cover routing, `[Authorize]`
  enforcement and exception mapping — none of which apply here. If the endpoint ever grows
  a real check, it earns a test then.

## 3. `curl` in the runtime image

`mcr.microsoft.com/dotnet/aspnet:10.0` ships neither `curl` nor `wget`, so the §1
healthcheck has nothing to run. One line in the final stage of `backend/Dockerfile`:

```dockerfile
RUN apt-get update && apt-get install -y --no-install-recommends curl \
    && rm -rf /var/lib/apt/lists/*
```

~5 MB, and the list cleanup keeps it from being more. This exists solely to serve the
healthcheck: if §2 is ever dropped, this goes with it.

The file's opening comment currently reads `# Build context: backend/ (Coolify "Base
Directory" = backend)`. The first half stays true — the compose file sets
`context: ./backend` — but the parenthetical becomes wrong, since Base Directory is now
`/` and the compose file supplies the context. Correct it to point at
`docker-compose.deploy.yml` instead.

## 4. Runbook — `docs/deployment-coolify.md`

A short click-path document, not a Coolify tutorial:

1. **Create the resource** — new resource → Docker Compose build pack → this git repo,
   and whichever branch is being deployed (Coolify redeploys on push to it).
2. **Point it at the file** — Base Directory `/`, Docker Compose Location
   `docker-compose.deploy.yml`. (Base Directory is `/`, not `backend`, because the
   compose file lives at the repo root and sets `context: ./backend` itself.)
3. **Set the six variables** from §1's table, each with "Build Variable" switched off.
   All six are declared `${...:?}`, so Coolify will refuse to deploy until they are
   filled — there is no way to accidentally ship a half-configured stack.
4. **Deploy**, and read the generated domain and Postgres password out of Coolify's
   environment panel — `SERVICE_PASSWORD_POSTGRES` is generated on first deploy and is
   the only copy.
5. **Verify** per §7.
6. **Redeploy and rollback** — what a redeploy does to the Postgres volume (nothing), and
   how to roll back to a previous deployment.

## 5. Local development is unaffected

Stated explicitly because it was the main concern raised during design. The dev flow runs
the API on the host with `dotnet run`; `dev-docker.ps1` only runs `docker compose up -d`,
and `docker-compose.yml` defines no `api` service.

| Change | Effect on `dev.ps1` / `start-dev.bat` / WSL Docker |
|---|---|
| `docker-compose.deploy.yml` | None — never auto-loaded. |
| `backend/Dockerfile` | None — nothing in the dev path builds it. |
| `docs/*` | None. |
| `Program.cs` | Adds an unauthenticated `/health` route. No new package, so no dependency-resolution risk; `dotnet run` and `dotnet test` behave as before. |

Reverting is `git checkout backend/src/TripPlanner.WebApi/Program.cs`. Nothing here is a
migration or a schema change.

## 6. Known gaps, accepted

- **`FRONTEND_URL` is wrong until the frontend ships.** Verification emails will link to
  whatever it is set to. Point it at the API's own domain as a placeholder; the accounts
  created before it is corrected simply need re-verifying.
- **Swagger is unavailable in production.** `Program.cs` gates `UseSwagger()` behind
  `app.Environment.IsDevelopment()`, and this design does not change that gate. Setting
  `ASPNETCORE_ENVIRONMENT=Development` to get Swagger back would also enable developer
  exception pages on a public host, which is a worse trade. Verify with `curl` instead.
- **No database backups.** Coolify's automated backups attach to its *managed* Postgres
  resource, not to a Postgres service inside a compose resource. Backing up
  `tripplanner-pgdata` is a separate piece of work, out of scope here.
- **Single instance.** One `api` container, no horizontal scaling. Migrations-on-startup
  assumes exactly that; two replicas booting together would race `MigrateAsync`.

## 7. Verification

After the first deploy:

1. `curl -f https://<domain>/health` → `Healthy`.
2. `curl "https://<domain>/api/destinations/locations?query=paris"` → results, proving the
   Geoapify key and the Redis cache path work. Repeat it and confirm the second call is
   faster (cache hit).
3. `POST /api/auth/register` → 200, proving Postgres is writable and migrations ran.
   Confirm the verification email arrives, proving the SMTP credentials.
4. Check Coolify's logs for the `api` service: no exceptions during startup, and the EF
   Core migration lines appear on the first deploy only.
5. Confirm `postgres` and `redis` have **no** public URL in Coolify's UI.
